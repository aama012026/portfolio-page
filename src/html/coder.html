Riftbound Collection Tracker

This WIP project tracks your collection of Riftbound TCG cards. It includes a lexer and parser that interprets the rules text on the cards in order to hide reminder text to be revealed on hover, mark up keywords, etc.

The project is written in typescript, sits on a hetzner server in germany running debian, and is built in bun with Datastar as its framework. The data is stored in and queried from a mariaDB relational database colocated on the server and communicating over localhost.

There's a sort bar above the table and a filter bar beneath. The boxes in the sort bar can be dragged to reorder the sort order. This is all done through Datastar signals, queried on the backend and patched on the client with a morphing strategy over SSE. The filters query and card count tracking has yet to be implemented.

If you're interested in looking at Datastar in action, take a look at the templates.html file and look for data-attributes like data-on:<event>, data-signals:<signal-name>, data-bind="<expression>", etc. The file includes custom variable markup used by my tiny HTML builder to generate js HTML-string construction functions.

If you want to look at the backend side, take a look at the SSE construction in sse.ts. The events are streamed to the client with a simple ReadableStream object. To see my go at writing SQL stored procedures and functions, have a look at either createProcedures.ts or createFunctions.ts under src/schema/.

Data-star: Making a performant but responsive website

Datastar is a tiny but powerful frontend framework (the entire library is a single 11.90KiB file) that replaces the need for heavy libraries like react while also outclassing the competition in raw performance. It does this somewhat ironically with two core principles:

  • Put state on the backend.
  • Let the browser do what it is built for.

It might seem strange for a frontend library's main feature to be its backend approach, but it does a couple of things for the developer and a couple of others for performance. Firstly, by moving most of the state (leaving UI) to the backend, the need for a clientside script often largely disappears or dramatically simplifies (the card gallery has no script besides the Datastar library). In its place, datastar uses custom data-* attributes (hence the name), to register signals in the DOM. Take a look at the html for a sortbox, the slanted boxes on the top of the card table that you can drag to reorder the sort priority on the table: 

<div class="sortbox badge-frame" draggable="true"
	data-on:dragstart="$_draggedIdx = %{idx: number}"
	data-on:dragend="@get('/cards')"
	data-on:dragover="evt.preventDefault()"
	data-on:dragenter="
		const targetValue = {...$sortOrder[%{idx}]};
		$sortOrder[%{idx}] = {...$sortOrder[$_draggedIdx]};
		$sortOrder[$_draggedIdx] = {...targetValue};
		$_draggedIdx = %{idx};
">
	<div class="badge" data-flex="align-center">
		<span data-text="$sortOrder[%{idx}].col" data-gradient="text">
		</span>
		<button class="symbol" data-gradient="text"
			data-text="$sortOrder[%{idx}].dir === 'ASC' ? '▼' : '▲'"
			data-on:click="
				if($sortOrder[%{idx}].dir === 'ASC') {
					$sortOrder[%{idx}].dir = 'DESC'
				}
				else {
					$sortOrder[%{idx}].dir = 'ASC'
				}
				@get('/cards')
		">
		</button>
	</div>
</div>

This is actually one of the wordier html-components. Most signals in datastar become simple hookups and toggles which, if you're familiar with react, you'll recognize the abstract patterns of. There are three types of Datastar signals in use here, although the %{} are mine. They tell the html builder to escape to a parameter, similarly to the raw {} to escape in .tsx:

  • data-on:<event> lets us register an event listener with access to our datastar signals. The signals are automatically created if they don't exist, and look like $signalName if inside an expression (Datastar converts between kebab-case and camelCase for signal names in attributes and expressions in order to follow the HTML-specs).
  • @get('/cards') sends a request to the server with the specified path. All signals are included in the request (as part of the url in case of the GET action) unless they begin with _.
  • data-text binds a signal to the textContent attribute of the element.

There are about 20 or so attributes and 9 actions in Datastar. This can greatly simplify the reactivity in the frontend, but most of the speedup comes from sending text to the browser directly, avoiding data synchronization and transformations in JS every time the server and client communicates.

Firstly, the DOM is really fast at ingesting text. Receiving and sending text is its primary mechanism after all. It is also incredibly good at compressing and decompressing text with a number of algorithms, so by compressing our responses we get both fast and efficient data transfers.

Secondly, we can minimize the connection overhead and time between sending a request and receiving the start of the response by keeping a long-lived connection open and sending an event stream. In fact, SSE is the primary and recommended way to update the client from the backend in Datastar. The pitch is twofold: As mentioned above, by updating the DOM directly, we bypass the slowest part of our website entirely. In addition, we propose that internet speed is generally not the bottleneck in modern web-dev. In fact, the creators of Datastar claims, and demonstrates on their website, that with SSE it is entirely doable to update the website at monitor refresh rates (144hz was the claim) from the backend.

Datastar has two types of server-sent events:

export function patchSignals(
	data: Record, onlyIfMissing: boolean = false
): string {
	const ssEvent = (
		`event: datastar-patch-signals\n` +
		`data: onlyIfMissing ${onlyIfMissing}\n` +
		`data: signals ${JSON.stringify(data)}\n\n`
	)
	return ssEvent
}

The datastar-patch-signals event can patch, update and remove signals. The naive function above also illustrates plainly the simple buildup of a SSE. Below is a function generating the second event type, datastar-patch-elements.

export function patchElements(
	elements: string, modifiers?: DatastarEventModifiers
): string {
	let ssEvent = `event: datastar-patch-elements\n`
	if(modifiers) {
		const {selector, mode, namespace, useViewTransition} = modifiers
		ssEvent += selector ? `data: selector ${selector}\n` : ''
		ssEvent += mode ? `data: mode ${mode}\n` : ''
		ssEvent += namespace ? `data: namespace ${namespace}\n` : ''
		ssEvent += useViewTransition ? `data: useViewTransition true\n` : ''
	}
	elements.split('\n').forEach(line => ssEvent += `data: elements ${line}\n`)
	ssEvent += '\n'
	return ssEvent
}

This one is a couple of lines longer to accomodate optional modifiers that can configure the event. By default, Datastar morphs the outer HTML of elements based on their ID, but other DOM morphing strategies are available, and you can use any valid CSS selector for the data: selector line. In fact, as the next snippet shows, my cards table is updated by first replacing the table body with the initial chunk of cards, then appending each following chunk to the table body.

I should mention that datastar has SDKs in over 15 languages including Typescript, but given that the two features above are really all you need to implement, making your own gives you full control and understanding as well as tailored flow and ergonomics should you wish.

That being said, let's look at how I update the card-table efficiently when the total response is approx. 5000 card rows and around 4.9-5.6MB in total: 

const CHUNK_SIZE = 50
const PREFERRED_ENCODING: Encoding[] = ['br','gzip']
async function* streamCardRows(rows: string[]) {
	if(rows.length === 0) {
		yield patchElements(makeCardsTableBody(''))
		return
	}
	// Replace the table body with the initial chunk
	yield patchElements(
		makeCardsTableBody(rows.slice(0, CHUNK_SIZE).join('\n'))
	)
	// Append every subsequent chunk
	for(let i = CHUNK_SIZE; i < rows.length; i += CHUNK_SIZE) {
		const elements = rows.slice(i, i + CHUNK_SIZE).join('\n')
		yield patchElements(
			elements, {selector: '#cards-table-body', mode: 'append'}
		)
		await Bun.sleep(0)
	}
}

This async generator takes an array of card rows HTML and chunks them up into Datastar events. We pass this to a function generating the SSE response: 

export function sseResponse(
	req: Request,
	events: AsyncIterable,
	serverTimings: string[],
	...preferredEncoding: Encoding[]
): Response {
	const headers: Record = {
		'Content-Type': 'text/event-stream',
		'Cache-Control': 'no-cache',
		'Vary': 'Accept-Encoding',
		'Server-Timing': serverTimings.join(', ')
	}
	// Pick an available text compression encoding from our preferred list.
	const encoding = pickEncoding(req, ...preferredEncoding)
	const stage = encoding ? encoders[encoding]() : new PassThrough()
	if(encoding) {headers['Content-Encoding'] = encoding}

	pipeline(Readable.from(events), stage, (err) => {
		// Premature close is the normal "aborted on client" case.
		if(err && (
			err as NodeJS.ErrnoException
		).code !== 'ERR_STREAM_PREMATURE_CLOSE') {
			console.error('SSE stream failed:', err)
		}
	})
	req.signal.addEventListener('abort', () => stage.destroy(), {once: true})

	return new Response(
		Readable.toWeb(stage) as ReadableStream, {headers}
	)
}

You can see that we take the request as an input parameter, as well as some server timings and an optional list of preffered text compression encodings. Note that we have to use the node stream API and then convert it to a web API readable stream. This is because we need to be able to flush the stream between chunks, which the node API exposes.

The snippet belows is how we pick our encoding. Put simply, we check the accept-encoding request header with a quality parameter higher than 0, and pick the first from our preferred that is available. For our /cards response this is generally Brotli with q=4, typically giving us a text compression of 48x. This is somewhat smaller than what brotli is capable of on larger pieces of text, and stems from a tradeof between compression quality and speed. We don't want to spend too long compressing small events. 

export function pickEncoding(
	req: Request, ...preferred: Encoding[]
): Encoding | null {
	const header = req.headers.get('accept-encoding') ?? ''
	const accepted = new Map()
	for(const part of header.split(',')) {
		const [name, ...params] = part.trim().toLowerCase().split(';')
		if(!name) {
			continue
		}
		const qParam = params.find(p => p.trim().startsWith('q='))
		const q = qParam ? Number(qParam.trim().slice(2)) : 1
		accepted.set(name.trim(), Number.isNaN(q) ? 0 : q)
	}
	for(const encoding of preferred) {
		/* An explicit entry wins over the `*` wildcard,
		so `br;q=0, *` still refuses br. */
		if((accepted.get(encoding) ?? accepted.get('*') ?? 0) > 0) {
			return encoding
		}
	}
	return null
}

So how does this compare to just sending all the card rows in a normal response?

Let's start with the baseline. From our server timings, we know that about 30-50ms is spent querying our database. Our database is a completely unoptimized, out of the box SQL database in mariaDB. Further, we spend about 80-150ms building the HTML markup for each card row after the query. This is the biggest time spend on the server, and could easily be optimized away by caching the HTML on either the database or server. Originally however, we spent about 150ms waiting on a response and 600ms - 900ms receiving it. That made the 150ms or so the server took to generate the response irrelevant. Even worse, a huge amount of time was spent while/after receiving on DOM style computation and layout, bringing the total time from reordering cards to seeing new cards on screen close to 3s!

Converting to a stream (But still just sending a single monolithic event) and adding text compression reduced the receiving time to around 200ms-300ms, but upped our waiting time to about 200-250ms. We shaved off around 500ms on average, which is huge, but largely unnoticable due to the majority of waiting happening on the client side. There's quite a bit of complicated and co-dependent CSS logic on the table, and some quick tricks can help out a bit, like setting content-visibility and content-intrinsic-size on table rows so that their dynamic height is not calculated before entering the viewport and is saved after they've been calculated even when they scroll out of view. The change, however, that actually matter here is making the table column widths fixed.

On its own, it shaves of maybe 50-100ms. Not that much. But this way, when we add the chunking to the SSE response, the DOM has to do substantially fewer style recalcs and layout changes. This reduces the time from the reorder event until you can start scrolling and interacting with the page to around 300ms, about a 16x improvement! So now the main chunk of response time is spent on the server, and remember, 150ms of these can be optimized away trivially.
